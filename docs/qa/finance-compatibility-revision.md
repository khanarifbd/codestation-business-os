## Implemented: legacy invoice detail links

Clients detail and payment history generate `/dashboard/finance/invoices/{encodedId}` links, but this route had no page. The existing `print` child did not supply its parent page. The new server page awaits Next's asynchronous `params` and redirects to the existing `/dashboard/accounting/invoices/{encodedId}` controller. It does not fetch data, change permissions, or execute financial actions. Empty and dot-segment IDs produce not-found rather than normalizing into a different route.

Canonical invoice detail currently accepts only `invoiceId`; its back link is the invoice register. Source Clients links carry no query intent. Therefore this narrow alias does not forward arbitrary `return_to`, `next`, or action query values. No supported query/return contract is discarded; a future compatible return design must be implemented explicitly in the canonical controller before extending this route. The existing print child remains byte-for-byte unchanged.

Verification: four executable Node tests transpile and call the actual server pages with mocked Next navigation. They cover a real-shaped ID, Unicode/slash/query/fragment/protocol-relative payload encoding, fixed same-origin destination, dot segments, ignored unsupported actions, source Clients links, canonical route wiring, and unchanged print routing. Scoped ESLint and `git diff --check` pass. No browser, full aggregate, live route, or deployed verification is claimed at this stage.
