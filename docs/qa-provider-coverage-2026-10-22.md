# External-provider coverage, 22 October 2026

This inventory comes from the implementation, not from dashboard labels. No provider credentials were read, configured or transmitted and no external calls were made during this QA pass. Local tests use a dedicated PostgreSQL database and loopback SMTP capture and provider transport fakes. Passing those tests is not evidence of actual email delivery, OAuth consent, settlement, payouts or production readiness.

## Implemented integrations and remaining sandbox checks

- **SMTP:** `app/services/account_email.py` constructs MIME text/HTML messages for verification, password reset, employee invitations and client portal invitations. A disposable loopback-only SMTP sink tests the actual smtplib transport, MIME and route-generated links without connecting to an external SMTP server. It does not relay mail, use credentials or test TLS. A separate authorized sandbox delivery test would require an SMTP test host/port, TLS mode, approved test sender and test inbox; SMTP username/password only if that sandbox requires them. `PUBLIC_APP_URL` must point to the test UI. Check receipt, link origin, spam placement and expiry separately. Production/staging requires SMTP configuration; local development can return `False` without delivery.
- **Google sign-in:** `app/services/google_identity.py` retrieves Google's public JWKS and validates ID-token signature, issuer, audience, expiry and verified email; `/auth/google` consumes credentials. Full sandbox browser validation needs a dedicated Google OAuth web client, matching configured backend and frontend client IDs, authorized test origins and explicit test account. Public-key fetching alone is not successful login. No Google tokens or credentials were used here.
- **Stripe:** `payment_gateways_stripe.py`, `stripe_checkout.py`, `stripe_lifecycle.py`, `stripe_settlement.py`, `stripe_payouts.py` and related services implement Connect/manual account setup, checkout, signed webhooks, settlement, refund/dispute and payout/accounting flows. Existing regression scripts use synthetic IDs, signed synthetic payloads and mocked provider responses, including scenarios named “live”; these names do not imply real live transactions. Authorized provider validation needs a dedicated test Stripe account/Connect test client, test secret key, test redirect URI, application gateway-encryption key, test webhook signing secret and a reachable test webhook endpoint. Manual test-key setup is an alternative to Connect where supported. Keep live collection disabled; no real bank account, live credential, charge or payout belongs in this pass.
- **Frankfurter exchange rates:** `app/api/v1/exchange_rates.py` uses `https://api.frankfurter.dev/v2/rate/{base}/{quote}`. No API secret is configured or needed by the implementation. Real-provider testing requires explicitly permitted outbound access and supported currency pairs; transport-response tests cannot establish provider availability or current rates. Frankfurter does not offer a distinct sandbox in this code.
- **WebAuthn/passkeys:** Browser authenticator flow, not an outbound account provider. Real end-to-end QA needs the expected RP ID/origin, secure browser context and an explicitly authorized test authenticator. Local challenge/credential fakes do not prove a physical authenticator flow.

## Not implemented as provider integrations

Client external profiles store descriptive links; they do not establish social-provider OAuth or synchronize accounts. Project credential storage is local encrypted data handling, not successful external authentication. Documents use local file storage, not S3 delivery. Other gateway labels must not be counted as implemented provider flows without a matching outbound adapter.

## Local coverage added

`backend/scripts/verify_qa_invitation_delivery_http.py` exercises the actual FastAPI app and actual authorization dependencies against isolated PostgreSQL. The request and rate-limit database factories point to rollback-only test transactions; the actual SMTP transport connects to a disposable loopback-only capture server. No auth or permission dependencies are bypassed. It checks signup/verification/resend/login, invalid/wrong-type/wrong-email/expired/version-revoked verification tokens, idempotent verification replay, delivery-failure rollback, employee/client invitation token rotation and single use, acceptance/login, permission denials and tenant boundaries. It deliberately distinguishes idempotent email verification from single-use invitation acceptance.

All synthetic accounts and invitations are rolled back. Local capture proves message construction and link flow, not delivery to a real inbox.

## Observed result and fixes

Final strengthened run: 73 expected HTTP responses and 13 MIME messages received through a real loopback SMTP connection. A post-rollback database check confirmed no synthetic user fixtures remained. The SMTP sink intentionally supports no authentication, TLS or relaying. Evidence: `invitation-owner-directory-final.log` in the isolated expanded-QA evidence directory.

The pre-fix regression reproduced successful employee invitation acceptance followed by a 403 password-login rejection. Employee acceptance now marks its email verified. Existing passwordless accounts fail closed with a 401 and guidance to sign in and set a password rather than passing a null hash to the password verifier. Both employee invitation preview and acceptance now reject roles from another organization. Tests verify the latter denial creates no user. The suite also verifies expired/revoked client invitations, existing-account wrong passwords, failed client-resend token preservation and explicitly reported employee delivery failures.

Remaining provider/browser boundary: actual external mail delivery, TLS, Google consent/login, physical passkeys and Stripe/Frankfurter service behavior were not exercised. These are separate from the local workflows proven here.

The strengthened HR06 scenario retains a real owner login session created before invitation acceptance. The owner remains authenticated as the same user and authorized to read the directory, whose new employee appears exactly once with the expected email, role and active statuses. Employee counts increase by one, the owner record is unchanged and a rejected acceptance replay leaves the full directory bundle unchanged.
